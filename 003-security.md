# ADR 003 — Проверка JWT на каждом уровне

Статус: принято.

## Контекст

Gateway должен фильтровать внешние запросы, но бизнес-сервисы могут быть доступны напрямую в локальной среде. Администратор каталога не должен вызывать протокол внутренних резервирований. Пользователь должен читать и отменять только собственные брони. Успешная регистрация не должна позволять самостоятельно назначить роль ADMIN.

## Решение

Пользовательские токены HS256 выпускает Booking Service после регистрации USER или проверки BCrypt-пароля. В токене используются `sub`, `exp`, `iss=hotel-booking`, `aud=hotel-api` и массив `roles`. Gateway и оба бизнес-сервиса работают как OAuth2 Resource Server и проверяют JWT самостоятельно. Фильтры не используют серверную HTTP-сессию.

Gateway сохраняет `Authorization`, разрешает публичные операции регистрации/входа и health, а остальные бизнес-запросы пропускает только после аутентификации. `@EnableMethodSecurity` и `@PreAuthorize` в сервисах проверяют USER/ADMIN/INTERNAL для конкретных операций. Проверка владельца брони использует `sub` токена, а не идентификатор пользователя из тела запроса. Запрос чужой брони получает `404`.

Для Booking → Hotel используется отдельный внутренний токен и отдельный секрет; роль INTERNAL не является ролью пользователя. Внутренние операции `confirm-availability` и `release` исключены из маршрутов Gateway и блокируются до пересылки, включая запросы с ADMIN. Знание пользовательского ключа не должно быть достаточным для выпуска внутреннего токена.

Ошибки аутентификации возвращают `401`, недостаток прав — `403` в общем JSON-контракте. `X-Request-Id` валидируется перед включением в ответ и логи; отсутствующее либо небезопасное значение заменяется UUID. Секреты, исходные пароли и JWT не логируются штатным кодом.

## Последствия

Защита бизнес-методов сохраняется при прямом обращении к сервисам и при будущей смене маршрутизации. Отключение CSRF соответствует stateless Bearer API без cookie-аутентификации; добавление браузерной cookie-сессии потребует пересмотра этого решения.

HS256 и демосекреты упрощают локальный запуск. Для отдельной среды нужно задать сильные разные ключи, TLS, защитить Eureka и внутренние порты, а также рассмотреть внешний issuer с асимметричными ключами и ротацией. В локальном примере Eureka не защищена пользовательским JWT и должна оставаться в доверенной сети.

Пользовательский JWT не отзывается мгновенно после выдачи: смена роли или удаление пользователя не является полноценным распределённым механизмом отзыва токенов. Срок действия токена ограничивает этот период; полноценный отзыв и смена паролей без повторного использования старых токенов требуют отдельного решения. Swagger и health открыты для удобства разработки; API каталога и бронирований остаётся защищённым.
