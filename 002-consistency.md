# ADR 002 — Локальная сага и атомарное резервирование

Статус: принято.

## Контекст

Booking и Hotel имеют независимые БД. Между подтверждением занятости и записью окончательного статуса возможны сетевые ошибки, повторы и параллельная отмена. Два клиента не должны одновременно занять один номер на пересекающиеся даты. Получение тайм-аута не доказывает, что удалённая операция не выполнена.

## Решение

Booking сначала фиксирует `PENDING`, затем сохраняет выбранный `roomId`, вызывает Hotel и завершает состояние как `CONFIRMED` либо `CANCELLED`. Локальные транзакции отделены от сетевых вызовов. `BookingStateService` блокирует записи для переходов состояний, чтобы позднее подтверждение не перезаписало отмену.

Идемпотентность внешнего запроса обеспечивается уникальностью `(user_id, request_id)`, блокировкой пользователя при подготовке и сравнением исходных параметров. Повтор возвращает уже имеющийся результат; использование ключа для другого payload отклоняется.

Hotel хранит локальное зеркало интервалов `room_reservations`. Внутри транзакции сервис блокирует строку номера `PESSIMISTIC_WRITE`, проверяет полуоткрытые интервалы `[startDate, endDate)` и записывает слот. Уникальность `(room_id, request_id)` предотвращает повторную вставку и повторный рост `timesBooked`.

Компенсация `release` идемпотентна. Она сохраняет `RELEASED` tombstone даже до появления исходного `confirm`: последующее подтверждение с этим ключом запрещено. Tombstone и мягкое удаление сохраняют историю доставки. Для новой попытки после отмены требуется новый `requestId`.

Если `release` не завершился, Booking сохраняет `compensationPending`. Фоновый восстановитель повторяет освобождение и отменяет зависшие `PENDING`. HTTP-клиент ограничивает время ожидания и число повторов; Circuit Breaker отклоняет новые допуски при серии временных сбоев, но не блокирует попытки компенсации.

## Последствия

Система обеспечивает атомарный допуск внутри Hotel и сходимость состояний при повторных доставках, пока доступны сохранённые данные обоих сервисов. Между шагами саги допустимо временное рассогласование. Резервирование разных номеров не требует глобальной блокировки. При автоматическом подборе устаревшая рекомендация безопасна: конфликт отсекает атомарный допуск, и координатор пробует следующего кандидата.

Это не XA/2PC и не гарантированная доставка через внешний брокер. Очередь компенсаций — флаг в записи бронирования. H2 in-memory ограничивает гарантию временем жизни процессов: после остановки нет данных для восстановления. Для эксплуатации нужны постоянные БД, миграции, контроль накопления tombstone и метрики незавершённых компенсаций. Самостоятельный перезапуск одной учебной БД не является поддерживаемым сценарием восстановления.

Отклонены: `synchronized` в памяти приложения — не работает между экземплярами; только предварительный поиск свободного номера — допускает гонку; удаление слота при компенсации без tombstone — позволяет опоздавшему подтверждению снова занять номер; удержание транзакции во время HTTP — не создаёт атомарности между БД и увеличивает время блокировок.
