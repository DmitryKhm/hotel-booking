# Booking Service

Spring MVC-приложение на порту `8081`, отдельная H2 `booking`. Регистрация, JWT, административные операции с пользователями и личные бронирования. Полная инструкция запуска находится в корневом README.

## API

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| POST | `/user/register` | публичный | Регистрация USER; `username`, `password` |
| POST | `/user/auth` | публичный | Вход; `username`, `password` |
| GET, POST, PATCH, DELETE | `/user` | ADMIN | Список, создание, обновление, удаление пользователей |
| GET, DELETE | `/user/{id}` | ADMIN | Получение/удаление пользователя |
| POST | `/booking` | USER/ADMIN | Создание личной брони |
| GET | `/bookings` | USER/ADMIN | Только своя история, `page`, `size`, `sort` |
| GET, DELETE | `/booking/{id}` | USER/ADMIN | Получение/отмена только своей брони |
| GET | `/swagger-ui/index.html` | публичный | OpenAPI UI |

POST `/booking`:

```json
{
  "requestId": "8b2844b2-1bd8-41f3-9e5a-fb817a120456",
  "roomId": 1,
  "autoSelect": false,
  "startDate": "2030-06-10",
  "endDate": "2030-06-13"
}
```

При `autoSelect=true` поле `roomId` игнорируется. Необязательный `hotelId` ограничивает рекомендации отелем. Заезд не раньше сегодняшней даты, выезд строго позже заезда, период не более 3650 ночей. Граница выезда исключительная.

POST/PATCH `/user` используют `role: "USER" | "ADMIN"`; PATCH также требует `id`. DELETE `/user` принимает query-параметр `id`. Удаление пользователя с историей бронирований возвращает `409`, сохраняя историю и внешние ключи. Пароли не возвращаются в API и хранятся как BCrypt-хеши.

Профиль `demo` создаёт пользователей `admin / Admin123!` и `demo / Demo123!`. Пароли переопределяются `DEMO_ADMIN_PASSWORD` и `DEMO_USER_PASSWORD`. За пределами демонстрации используйте другой профиль и создавайте данные отдельно.

## Согласованность и повторные запросы

1. Короткая локальная транзакция фиксирует PENDING. Уникальный ключ `(user_id, request_id)` и блокировка строки пользователя не допускают дубли при параллельной доставке.
2. Сервис сохраняет выбранный roomId и вне транзакции запрашивает Hotel Service. При автоназначении кандидаты упорядочены по `timesBooked`, затем `id`; `409` приводит к следующему кандидату.
3. Успех фиксирует CONFIRMED. Ошибка/тайм-аут фиксирует CANCELLED и необходимость компенсации. Все переходы блокируют строку бронирования, поэтому запоздалый успех не отменяет отмену пользователя.
4. Release идемпотентен. Флаг `compensationPending` хранится до успешного снятия слота. Планировщик повторяет компенсацию после восстановления Hotel Service и отменяет зависшие PENDING старше 60 секунд. Hotel хранит tombstone для release-before-confirm, поэтому поздний confirm не создаёт потерянную блокировку.

Повторный POST с тем же пользователем, requestId и параметрами возвращает существующую бронь (`200`), включая PENDING/CANCELLED. Повторное использование ключа с другим содержимым возвращает `409`. Для новой попытки после отмены нужен новый requestId. DELETE возвращает `204`; если Hotel недоступен, отмена уже записана, а `compensationPending=true` показывает, что освобождение слота ещё выполняется. Все данные, в том числе очередь компенсаций, теряются при перезапуске in-memory H2: гарантия восстановления действует в пределах жизни БД, как предусмотрено учебным ТЗ.

HTTP имеет connect/read timeouts 800/1500 мс, максимум 3 попытки и backoff 100/200 мс. Повторяются только транспортные сбои, 429 и 5xx. Circuit breaker учитывает последние 10 вызовов, открывается после минимум 5 вызовов при 60% ошибок на 5 секунд. Компенсация проходит с теми же ограниченными повторами, но обходит circuit breaker новых бронирований.

По умолчанию адрес `http://hotel-service` разрешается через Eureka. Для прямого подключения задайте одновременно `HOTEL_DISCOVERY_ENABLED=false` и `HOTEL_SERVICE_URL=http://localhost:8082`.

Тесты запускаются из корня: `./mvnw -pl booking-service -am test`. Они проверяют Saga, реальные HTTP-тайм-ауты, Retry/CircuitBreaker, JWT, роли, приватность истории, параллельные дубли и гонку подтверждения с отменой.
